# v3.51.2

## 优化改进

- 分层调度：优先消耗老号保留容量，消耗层沿用额度重置优先，承接层按每个账号的有效容量占用比例分配流量
- 持续均衡：原老号退出后，启用交接组策略的订阅账号继续均衡；账号进入消耗阶段只改变优先级，不自动将原承接账号互相绑定成新老关系
- 多账号交接：指定承接池优先于组外普通账号，分别保留各新号的保护档位，后补账号不重置已有账号的保护进度

## 问题修复

- 新增流量不再被老号入组时的并发基线封顶，增长流量和转出流量共用新号已有保护容量
- 初次减载不超过现有承接空位，后续降档扣除新号实际占用及上一档尚未排空的老号请求，空间不足时保持当前档位
- 承接失败回退不再反向增加转移预算，容量缩小时旧在途仍计入共享上限，避免重复放行
- 无限并发账号不再被当作零负载参与承接均衡，使用保护完成容量作为比较参考，保留原始无限并发语义
- 陈旧或未来时间的额度观测不用于消耗层的额度阈值判定

## 升级须知

- 相对 v3.51.1 没有新增数据库迁移或配置字段，现有交接参数保留；持续分层调度须启用自动策略并配置交接组与新号保护
- 全组转移预算只控制老号减载量，不再充当全部新号的总承接上限；各账号保护上限及 Redis 原子容量检查继续生效
- 软会话偏好允许重新选号，固定续接、严格亲和、跟随线程、管理员权重、模型权限和 Guardian 独立池保留原合同
- 均衡按并发占用比例，不保证请求数、Token 或费用完全相等；老号额度能否用尽仍取决于真实流量和剩余有效时间
- 从 v3.49.2 升级仍包含 v3.51.1 的迁移 0046 和 scheduler v4 接口变化；独立补号插件不随主程序发布
- 保留此前明确批准的 picomatch `GHSA-fc5q-39xc-vjpf` 构建依赖单项审计例外，其他安全检查保持启用
- 本次发布不自动升级、重启线上实例或开启新功能
